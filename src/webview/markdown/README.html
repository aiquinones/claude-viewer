webview/markdown

Raw markdown text in, React elements out, with every heading pinned to the top of the pane while you are inside its section. Two data shapes carry the whole folder: a token, which comes from marked, and a section, which this folder builds on top of them.

Read the example first, then open the sections below — each one explains one piece of it.

The example

One small SKILL.md body. Everything below refers back to it.

Read this before editing.

# Setup

Install with `pnpm install`.

### Requirements

- Node 20+
- **pnpm**, not npm

# Usage

See the [build docs](https://example.com).

Four things in there matter, and each one hits a different corner of the code:

  • A paragraph before any heading — it belongs to no section.
  • # Setup jumping straight to ### Requirements, skipping ##.
  • A list whose item holds inline formatting (**pnpm**).
  • A link, which renders differently depending on where it points.

1. A token

marked's output — a flat list

marked.lexer(raw) turns the text into a flat array of tokens. Flat: the two headings below are siblings of the paragraphs, not parents of them. Nothing in that array says Requirements is inside Setup.

The example lexes to exactly this — token type on the left, the source it came from on the right:

paragraph    "Read this before editing."
space        "\n\n"
heading      "# Setup"
space        "\n\n"
paragraph    "Install with `pnpm install`."
space        "\n\n"
heading      "### Requirements"
space        "\n\n"
list         "- Node 20+\n- **pnpm**, not npm"
space        "\n\n"
heading      "# Usage"
space        "\n\n"
paragraph    "See the [build docs](https://example.com)."

Every token has a type and a raw (the source text it consumed). Beyond that the fields depend on the type: a heading has depth (the number of #), a list has items, a table has header and rows.

Tokens nest inside tokens

The flat list is only the top level. A token that contains formatted text carries its own tokens array. The last paragraph of the example, fully expanded:

{
  "type": "paragraph",
  "raw":  "See the [build docs](https://example.com).",
  "tokens": [
    { "type": "text", "text": "See the " },
    {
      "type": "link",
      "href": "https://example.com",
      "text": "build docs",
      "tokens": [ { "type": "text", "text": "build docs" } ]
    },
    { "type": "text", "text": "." }
  ]
}

That recursion is why rendering is two functions rather than one. Blocks.tsx handles tokens that occupy vertical space (paragraph, list, code, table, blockquote, hr) and Inline.tsx handles the ones that live inside a line (text, strong, em, codespan, link, image, br). Each one recurses into the other where it needs to: a list item's content goes back through Blocks, a paragraph's tokens go through Inline.

The space tokens are dropped. toSections skips them — blank lines are already implied by the block structure, and vertical rhythm comes from CSS margins in Blocks.tsx. Those margins are plain margin on purpose, so adjacent blocks collapse into one gap; that only works while the container stays normal flow, never flex.

Why isToken exists

marked types its output as a union, Token. You would expect token.type === 'list' to narrow it to Tokens.List. It doesn't quite: the union carries a Generic member whose type is a plain string, so string matches every comparison and the check narrows to "the real one, or Generic". Generic declares most fields optional, so token.items stays possibly undefined and the code fills with guards that can never fire.

// tokens.ts
export type TokenOf<Type extends string> = Extract<Token, { type: Type }>;

export const isToken = <Type extends string>(token: Token, type: Type): token is TokenOf<Type> =>
  token.type === type;

TokenOf<'list'> is Tokens.List and nothing else, and the guard asserts it. Use isToken for any token whose fields you actually read (list, table, link, image, heading); a plain === is fine when you only need text or raw, which Generic types the same way.

2. A section

this folder's shape — a tree

A Section is one heading plus everything under it: the blocks that follow it, and the sub-sections nested inside it.

export interface Section {
  // Absent on the one section that holds whatever came before the first heading.
  heading?: Tokens.Heading;
  // Position in the tree, 1-based — not the markdown level.
  depth: number;
  blocks: Token[];
  children: Section[];
}

toSections turns the flat token list into these. The example becomes:

(preamble)          depth=0   blocks=[paragraph]
# Setup             depth=1   blocks=[paragraph]
    ### Requirements    depth=2   blocks=[list]
# Usage             depth=1   blocks=[paragraph]

Read that against the source and three rules fall out.

Blocks belong to the heading above them

blocks holds only what sits directly under that heading, before the next one. Setup owns the Install with… paragraph but not the list — the list arrived after ### Requirements, so it belongs to Requirements. To render a whole section you render its blocks, then recurse into children.

Depth is position in the tree, not the number of hashes

This is the one that surprises people. ### Requirements is a level-3 heading, but it is the first thing nested under # Setup, so its depth is 2, not 3. The jump from # to ### costs one step of nesting, not two.

Both numbers survive, and each has a job:

NumberWhere it livesWhat it drives
section.depth computed by toSections the sticky top offset and the heading's visual weight
heading.depth marked, straight from the #s which HTML tag gets emitted (h1…h6)

So Requirements renders as an <h3> — honest to the source, and correct for a screen reader — while being styled and offset as the second bar in the stack. If depth used the hash count, a file that jumped # → ### would leave an empty slot in the sticky stack and the second bar would float with a gap above it.

The preamble section has no heading

Read this before editing. comes before any heading, so it has no section to belong to. Rather than dropping it, toSections opens one section with heading: undefined and depth: 0. SectionView renders its blocks and skips the sticky bar. It is the only section that can lack a heading, and the only one at depth 0 — real sections start at 1.

3. How the tree gets built

toSections, one pass, one stack

One pass over the tokens, holding a stack of the sections currently open — outermost first. The stack is the path from the root down to wherever the next token would land.

if (isToken(token, 'heading')) {
  // Close every open section this heading is not inside.
  while (open.length > 0 && open[open.length - 1].level >= token.depth) open.pop();

  const parent = open[open.length - 1];
  const section = { heading: token, depth: open.length + 1, blocks: [], children: [] };
  (parent ? parent.section.children : roots).push(section);
  open.push({ level: token.depth, section });
  continue;
}

// Not a heading: it belongs to whatever is open.
open[open.length - 1].section.blocks.push(token);

Two separate numbers do the work here, which is worth pausing on:

  • level — the markdown level, kept on the stack entry. It decides how much a new heading closes: pop while the open level is >= the new one. A ## closes another ## and any ### under it, but not the # above.
  • depth — read off open.length at the moment the section is created. Because it counts what is on the stack rather than hashes, the # → ### jump collapses to one step automatically. No special case anywhere.

The example, step by step

TokenStack afterWhat happened
paragraphemptynothing open → opens the preamble
# Setup[1]nothing to pop; a root section, depth = 0 + 1
paragraph[1]pushed onto Setup's blocks
### Requirements[1, 3]1 >= 3 is false, so nothing pops — child of Setup, depth = 1 + 1

# Usage[1]3 >= 1 and 1 >= 1, so both pop — back to a root section

4. Why a tree at all

the sticky headings depend on it

The tree is not for tidiness — the pinning does not work without it.

A position: sticky element stops sticking when its containing block scrolls out of view. That gives the nesting a job: render sections as nested <section> elements and each heading's containing block is exactly its own section, so a ## unpins the moment you leave it.

<section>                    <!-- # Setup -->
  <h1 sticky top: 0>
  <p>Install with…</p>
  <section>                  <!-- ### Requirements, inside Setup -->
    <h3 sticky top: 1.75rem>
    <ul>…</ul>
  </section>
</section>
<section>                    <!-- # Usage -->
  <h1 sticky top: 0>
</section>

Flatten that — every heading a sibling in one long div — and they all share one containing block, the div. Nothing releases until the entire document scrolls past. Scroll from Requirements into Usage and the Requirements bar stays pinned under it forever, labelling content it has nothing to do with.

The offsets

Markdown.tsx stacks the bars by giving each one a top equal to the height of everything above it:

const ROW_REM = 1.75;   // matches `h-7` on the heading — change one, change the other
const MAX_DEPTH = 4;    // past this the bars would eat the pane

top: `${(Math.min(section.depth, MAX_DEPTH) - 1) * ROW_REM}rem`
zIndex: 30 - depth      // an outer bar covers an inner one sliding under it

Depth 1 sits at 0, depth 2 at 1.75rem, depth 3 at 3.5rem. Deeper than 4 and headings share the last slot rather than pushing the stack further down the pane.

Every bar has to be exactly one row tall. The offsets are multiples of ROW_REM, so a heading that wrapped to two lines would push its own content down without moving any of the offsets below it, and the stack would overlap from there on. That is why the heading is a fixed h-7 and its text truncates with an ellipsis instead of wrapping. The <span> inside does the truncating, not the heading — a flex item needs min-w-0 before it will shrink far enough to show one.

5. Rendering

Markdown → SectionView → Blocks / Inline

Four components, each one small:

Markdown        toSections(raw), then one SectionView per root
  SectionView   the sticky heading, its blocks, then its children — recursive
    Blocks      block tokens → <p> <ul> <pre> <table> <blockquote> <hr>
      Inline    inline tokens → <strong> <em> <code> <a> text

Both renderers are an if-chain over token.type with a fallback at the end, so an unrecognised token degrades instead of crashing the pane — Blocks returns null and skips it, Inline falls back to the token's raw source so a stray inline construct still shows its text. That matters here: the input is whatever someone wrote in a SKILL.md, and config formats drift between Claude Code releases.

Three deliberate non-renders

These look like gaps and are not — each one is a decision, all three in Inline.tsx:

InputRenders asWhy
An image image: alt text in a muted chip The panel's CSP has no img-src, and a skill's own files are not a localResourceRoot. It could not load, so it says what it is instead.
A link that is not http(s): or mailto: dotted underline, not a link, target in the tooltip A relative path or an anchor would navigate the webview itself off its shell and take the panel with it. Only external links get an <a>.
Raw HTML its source text, verbatim Showing what is actually in the file beats parsing it, and beats dropping it silently.

The tight-list quirk

In the example, - **pnpm**, not npm reaches Blocks as a block-level token of type text — not a paragraph, because the list is tight (no blank lines between items). If it rendered as a <p> the text would drop to its own line below the bullet. So Blocks renders that one case inline, and the bullet keeps its text:

if (token.type === 'text') {
  return 'tokens' in token && token.tokens?.length ? <Inline tokens={token.tokens} /> : token.text;
}

The same shape shows up in Inline: a text token carries its own tokens only when something inline is nested in it, so both renderers check before recursing and fall back to the plain string.

If you add a token type

  1. Decide block or inline; that picks the file.
  2. Add the branch to that file's render. Use isToken if you read fields beyond text or raw.
  3. Add a story covering it — including how it looks empty or malformed, since real config will not reliably show you either.

Adding a token type never touches sections.ts. The tree only cares which tokens are headings; everything else is an opaque block it files under one.
